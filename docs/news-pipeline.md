# 新闻采集与「新闻 ↔ 股票」关联

> 目的：给 B3「事件发生后自动检索相关信息」提供有历史、可检索、能落到具体股票的新闻底料。
> 所有数字均为实测。

## 一、为什么需要回溯

财联社快讯只返回**当日 20 条**、个股新闻只给**最近 10 条**，都没有分页参数。
也就是说**新闻是不可回查的流**——今天不采，昨天的就没了。

但实测发现两个源都支持**向前翻页**，所以历史可以事后补齐：

| 源 | 接口 | 回溯能力 |
|---|---|---|
| 东财新闻列表 | `np-listapi.eastmoney.com/.../getNewsByColumns` | ✅ `page_index` 翻页，实测可回溯 **48+ 天**，约 99 条/天 |
| 财联社电报 | `www.cls.cn/v1/roll/get_roll_list` | ✅ `last_time` 翻页（需自算 `sign`），约 32 条/小时 |

> 财联社的 `sign = md5(sha1(urlencode(params)).hexdigest())`。
> akshare 的 `stock_info_global_cls` 只取第一页、没暴露 `last_time`，所以这里自己实现。

### 回溯窗口有多深（实测）

不用一页页翻，直接把时间戳/页码指到很久以前看还能不能取到：

| 源 | 实测上限 | 依据 |
|---|---|---|
| 东财新闻列表 | **约 200 天** | page 1200 = 201 天前；page 2000 返回同一天 → 到底了 |
| 财联社电报 | **≥ 180 天** | `last_time` 指到 180 天前仍返回 20 条正常数据 |

**结论：不需要 7×24 挂着采。** 只要断档不超过 ~6 个月，随时能补回来。

**结论：不需要 7×24 挂着采**。断线几天，用 backfill 都能补回来。

## 二、模块结构

```
backend/app/
├── db.py                        # 连接、建表、视图、股票同步
└── providers/
    ├── news_sources.py          # 取数：东财翻页 / 财联社翻页 / 快照
    ├── news_store.py            # 归一化 → 去重 → 入库 → 触发关联
    └── stock_link.py            # 实体链接：正文 -> 股票代码
scripts/
├── backfill_news.py             # 历史回溯
└── run_collector.py             # 实时采集（不是自动运行，见第五节）
```

## 三、数据模型

库文件：`data/news.db`（已被 `.gitignore` 忽略，可随时重建）

```sql
news(id PK, source, channel, title, content, published_at, url,
     content_hash UNIQUE, fetched_at)

stock(code PK, name, industry_l1_name)          -- 从申万映射表同步

news_stock(news_id, stock_code, stock_name,
           match_type, confidence)               -- 多对多，主键(news_id, stock_code)

collect_log(id, run_at, source, fetched, inserted, skipped, linked, note)

news_fts                                        -- FTS5 trigram 全文索引
v_news_stock_high                               -- confidence >= 0.85 的关联视图
```

- **去重**：`content_hash = md5(归一化标题 | 正文前 400 字)`，`UNIQUE` 约束保证幂等，
  重复跑不会产生重复行。
- **全文检索**：FTS5 用 `trigram` tokenizer（中文子串可搜），退化时用 `unicode61`。

## 四、实体链接：新闻 → 股票

`stock_link.py` 用两条通道：

| 通道 | 规则 | match_type | 置信度 |
|---|---|---|---|
| 代码 | 正文出现 6 位 A 股代码（`600519` / `600519.SH`），且该代码在股票表里 | `code` | **1.00** |
| 名称 | 公司简称（≥3 字）出现在正文 | `name` | 见下 |

**名称通道按长度分档**（这是关键）：

| 简称长度 | 置信度 | 原因 |
|---|---|---|
| ≥4 字 | **0.90** | 基本不会误匹配 |
| 3 字 | 0.70 | 容易命中通用词 |
| 命中 `AMBIGUOUS_NAMES` | 0.40 | 见下 |
| 去 ST/N 前缀后的别名 | -0.05 | 略降 |

### 为什么要有歧义名单

实测踩到了：**`300024` 的简称就是「机器人」**，而「人形机器人赛道全线爆发」这类新闻满天飞。
第一版不分档时，它关联了 **283 条**，远超第二名（宁德时代 104 条）——纯噪声。

处理方式是**保留原始关联但降权**，并提供一个高置信度视图：

```sql
-- 默认查询走这个
SELECT * FROM v_news_stock_high WHERE stock_code = '600519';
```

这样既不丢信息（可追溯），默认查询又干净。实测过滤后 Top8 全部是合理标的。

### 性能

不遍历 4000 个股票名去 `in` 文本（太慢），而是对每条文本生成 3~8 字 n-gram 再查字典。
一条 200 字新闻约 1200 次哈希查找，6600 条新闻全量关联耗时 < 2 秒。

## 五、用法

### 回溯补齐（推荐先跑这个）

```bash
# 东财 30 天 + 财联社 7 天（首次约 2~3 分钟）
python scripts/backfill_news.py

# 只补东财，拉满 48 天
python scripts/backfill_news.py --days 48 --no-cls

# 增量：已采过的会自动跳过（靠 content_hash）
python scripts/backfill_news.py --days 3

# 改了链接词典后，重算已有新闻的关联
python scripts/backfill_news.py --rebuild-links
```

关键参数：`--days` `--cls-days` `--delay` `--max-pages` `--stop-on-known`
（`--stop-on-known` 表示连续多少页全是重复数据就停，增量跑时很快结束）。

### 运行节奏：不用每天

因为两条源都能回溯约半年，**没必要每天跑**。按场景选：

| 场景 | 命令 | 耗时 | 说明 |
|---|---|---|---|
| **平时（每 1~2 周一次）** | `python scripts/backfill_news.py --auto` | 1~3 分钟 | 自动算出断档天数，已采过的页快速跳过 |
| 演示 / 提交前 | `python scripts/backfill_news.py --days 60 --no-cls` | 5~8 分钟 | 只补东财，把历史拉厚 |
| 一次性补满 | `python scripts/backfill_news.py --days 180 --no-cls` | 约 15~20 分钟 | 东财 1000 页左右 |
| 想要财联社的深度历史 | `--days 30 --cls-days 30` | 约 20 分钟 | ⚠️ 财联社约 28 页/天，比东财贵 3 倍 |

`--auto` 会读库里最新一条新闻的时间，自动决定补多少天：

```
[auto] 库中最新新闻 2026-10-28 15:10:29，已断 0 天
[auto] -> 东财补 2 天，财联社补 1 天
```

**唯一硬约束：断档别超过 ~190 天**，否则会越过东财 200 天的上限，更早的新闻永久丢失。
脚本在接近该阈值时会打印警告。

### 为什么不需要常驻采集

区分两件事：

| 需求 | 解法 | 是否需要 7×24 |
|---|---|---|
| **历史证据**（事件调查时回看「当时发生了什么」） | 定期 backfill | ❌ 不需要 |
| **最新动态**（事件触发后立刻找当天新闻） | 事件发生时现拉快照（20~200 条）即可 | ❌ 不需要 |

也就是说：**库里存历史，调查时现拉最新**。两头都不依赖常驻进程。

### 实时采集

```bash
python scripts/run_collector.py --once          # 跑一轮
python scripts/run_collector.py                 # 每 300 秒一轮，前台常驻
python scripts/run_collector.py --gap-fill 1    # 每轮前先补最近 1 天的洞
```

> ⚠️ **这不是「开机自动运行」**。它只是一个进程，你不启动就不跑，电脑关机就断。
> 配套方案是定期跑 `backfill_news.py` 补洞——因为东财能回溯 48 天，断一周也能补。

## 七、这次踩到的坑

1. **东财正文读不到**：列表接口的摘要字段叫 **`summary`**，不是 `digest` / `content`。
   第一版写错了字段名，导致 2994 条新闻全部没有正文、关联率只有 15%。
   修正后关联率升到 **30.6%**。
2. **`content_hash` 会把正文变更当成新记录**：改了字段名后必须**先删旧行再重采**，
   否则同一条新闻会因为正文从空变成非空而被当成两条。
3. **3 字简称噪声**：见第四节。
4. **`str(nan)` 落成字符串 `"nan"`**：CSV 往返时会被读回真正的 `NaN`，撞 `NOT NULL`。
   已在 `txt()` 里统一处理。

## 八、已知限制

| 限制 | 影响 | 后续 |
|---|---|---|
| 个股维度的历史新闻补不回来 | `stock_news_em` 只有最近 10 条 | 靠「全市场新闻 + 实体链接」覆盖，已实现 |
| 东财只采了 `column=345` 一个栏目 | 可能漏掉其他分类 | 可加栏目号扩展 |
| 财联社回溯成本较高（约 38 请求/天） | 长周期回溯慢 | 东财为主、财联社为辅 |
| 没有采集新闻详情页全文 | 只有列表摘要（中位 141 字） | 需要长文时再按 URL 抓 |

## 九、和 B3 的衔接

事件发生后「检索相关新闻」只需要一条 SQL：

```sql
SELECT published_at, source, title, url
FROM v_news_stock_high
WHERE stock_code = '600519'
  AND published_at BETWEEN '2026-10-01' AND '2026-10-28'
ORDER BY published_at DESC;
```

或者用 `news_store.search(con, stock_code=..., start=..., keyword=...)`。

每条结果都带 `url` 和 `published_at`，可以直接作为 `Evidence` 对象（来源 + 时间 + 链接），
满足 C4「用户能查看支撑结论的依据」。
