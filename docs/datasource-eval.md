# 数据源评估（Step 0 / 可行性验证）

> 实测日期：2026-10-28 ｜ 环境：akshare 1.20.1 / PyMuPDF 2.0 / baostock 0.9.40 / pypdf ｜ 探针标的：600519 贵州茅台
> 共 6 轮探针（`scripts/probes/01` ~ `09`），实测 25+ 接口，全部结论均有脚本与原始输出存证

## 一、核心结论

1. **没有任何单一数据源同时把「行情 + 公告 + 新闻」都做好**，但也不需要装很多库。`akshare` 本身是**多源聚合客户端**（底层对接东财、新浪、巨潮、财联社、百度、同花顺），所以「代码层面一个依赖，数据层面多源组合」。
2. **公告 PDF 全文链路已完全打通**：巨潮官方接口 → 直链下载 → 正文抽取，单份 110 页年报 0.9s 内完成。C4（证据追溯）与 D2（多步调查）的数据基础成立。
3. **⚠️ 东财的「前复权」收盘价不能直接用来算收益率**——已用数学恒等式证明其口径不符。这是一个会直接算错所有指标的问题。
4. **⚠️ 东财限频会进入「持续拒绝」状态**，不只是偶发失败。实测退避能救回单次请求，但当连续调用多个东财接口后，指数、行业板块等接口会**连续 3 次全部失败**。因此**指数与行业数据必须有非东财备源**——§十 已验证：指数 4 个源、行业 3 个源全部可用。
5. **估值比率不需要依赖百度**：baostock 的日频 K 线查询可直接返回 `peTTM / pbMRQ / psTTM / pcfNcfTTM / turn`，与行情同一次请求拿到，天然对齐、无需二次拼装。

## 三、三种信息的时间粒度不同（重要架构含义）

| 维度 | 粒度 | 可回查历史？ | 结论 |
|---|---|---|---|
| 行情 | 日频 | ✅ 任意区间 | 按需拉取 + 缓存 |
| 财务 | 季频 | ✅ 20+ 年 | 按需拉取 + 缓存 |
| **新闻/快讯** | **流式** | ❌ **只给当日 20 条 / 个股最近 10 条** | **必须持续抓取并落库，过期不可回查** |

> 已实测确认：财联社 `stock_info_global_cls` 仅接受 `symbol={"全部","重点"}`，**无日期参数、无分页**，单次返回 20 条且只覆盖当天。东财个股新闻只有最近 10 条（2026-10-21 ~ 2026-10-28）。
> → **新闻采集器 + 本地落库必须在第二阶段就上线，不能等第三阶段。**

## 四、新闻关联是 B3 的核心难点

新闻接口是**全市场维度**，不是按股票返回的；个股接口量太小。因此「事件 → 检索相关新闻」需要自己做**实体链接（Entity Linking）**：

1. 从快讯正文抽取股票代码（`600519.SH`）、全称（`贵州茅台`）、简称（`茅台`）
2. 建立「新闻 ↔ 股票」多对多关系表
3. 用公司简称/曾用名/产业链关键词词典增强召回

这是本项目技术难点之一，也是「附证据的解释」能否成立的关键。

## 五、公告 PDF 全文链路（✅ 已验证可用）

这是 C4「用户能查看支撑结论的关键数据」和 D2「多步调查」的地基。

### 5.1 链路

```
① 巨潮官方查询 API  POST http://www.cninfo.com.cn/new/hisAnnouncement/query
   └─ 返回 announcementId / adjunctUrl / announcementType / adjunctSize
② 直链下载         http://static.cninfo.com.cn/{adjunctUrl}
   └─ 例：finalpage/2026-08-15/1225475868.PDF
③ 正文抽取         PyMuPDF (pymupdf.open → page.get_text())
④ 落库             Evidence{来源=巨潮, URL, 发布日期, 页码, 原文片段}
```

### 5.2 实测数据

| 环节 | 结果 |
|---|---|
| 公告列表 | 155 条 / 1.1s |
| 官方 API 定位直链 | 30 条 / **0.2s**，直接给 `adjunctUrl`，**无需拼 URL** |
| PDF 下载 | 4 份全部 200，94 KB ~ 813 KB，**0.1 ~ 0.8s**，`Content-Type: application/pdf` |
| 正文抽取（PyMuPDF） | 110 页半年报 → **118,001 字符 / 57,845 中文字，0.15s** |
| 正文抽取（pypdf 对照） | 同文档 4.14s，**慢 27 倍**，字符数一致 |

**抽出的正文质量**（真实预览，可直接作为 Evidence 引用）：

> 贵州茅台酒股份有限公司2026 年半年度报告 1 / 110 公司代码：600519 公司简称：贵州茅台 … 重要提示 一、本公司董事会及董事、高级管理人员保证半年度报告内容的真实性、准确性、完整性…

> 1 证券简称：贵州茅台 证券代码：600519 编号：临2026－030 贵州茅台酒股份有限公司 关于会计政策变更的公告 … 重要内容提示：●…根据中华人民共和国财政部相关规定进行的会计政策变更，不会对公司财务状况、经营成果和现金流量产生重大影响…

### 5.3 结论

- **PDF 是文本型而非扫描件**，无需 OCR，抽取质量足够做「原文段落级引用」
- **用 PyMuPDF，不要用 pypdf**（27 倍速度差）
- 优先用官方查询 API 拿 `adjunctUrl`，**不要靠日期+ID 猜测静态地址**
- 请求需带 `User-Agent` 与 `Referer: http://www.cninfo.com.cn/`

### 5.4 遗留

- 巨潮返回的 `announcementTypeName` **实测为空**，只有数字编码（如 `010113`、`01010503`）
- → 事件分类标签**用东财的 `公告类型` 文本字段**（87 种，见下节），巨潮编码仅作辅助

## 七、⚠️ 复权口径：一个会算错所有指标的问题

### 7.1 复权三态差异有多大

同区间（2024-01-01 ~ 2026-10-28，681 个交易日）600519：

| 口径 | 区间累计收益 |
|---|---|
| 前复权 qfq | **−14.07%** |
| 不复权 raw | **−20.90%** |

**差 6.83 个百分点**。681 个交易日中有 **90 天（13%）** 的日收益在两种口径下相差 >0.1%。期内发生 **5 次除权除息**（2024-06-19、2024-12-20、2025-06-26、2025-12-19、2026-06-26），复权因子约 0.928 / 0.942 / 0.961…

### 7.2 两个源的前复权结果不一致

东财 qfq vs baostock 前复权（**680 个重叠交易日**，2024-01-02 ~ 2026-10-27，同一区间基准）：

| 指标 | 东财 qfq | baostock 前复权 | 差异 |
|---|---|---|---|
| 区间累计收益 | −12.56% | −11.45% | **1.11 pp** |
| **年化波动率** | **24.54%** | **23.31%** | **1.23 pp** |
| 日收益相关系数 | 0.99960 | | |
| 日收益差异均值 | 0.047% | | |
| 日收益差异最大 | 0.786% | | |
| 价格比值 close_bs/close_em | 均值 0.9955，极差 2.72% | | |

> 注：§7.1 的 −14.07% / −20.90% 基于 681 个交易日（2024-01-01 起），与本表的 680 日基准不同，故数值略有差异，不影响结论。

> 收益率序列高度相关但**不相等**，累计收益差 1.1pp、波动率差 1.2pp —— **不可混用**。

### 7.3 决定性检验：哪家的复权是对的

数学恒等式：**非除权日，复权收益率必须等于不复权收益率**（复权只在除权日改变收益序列）。

| 数据源 | 非除权日 \|复权收益 − 不复权收益\| | 判定 |
|---|---|---|
| **baostock 前复权** | 最大 **0.00000000**，674 天全部一致 | ✅ **口径正确** |
| **东财 qfq** | 最大 **0.007865**，**470 / 675 天不一致** | ❌ **口径有误** |

差异最大的几天集中在 2024-09-24 ~ 2024-10-09（9·24 行情大涨段）：

| 日期 | 东财 qfq 收益 | baostock 收益 | 差 |
|---|---|---|---|
| 2024-09-24 | +9.5900% | +8.8035% | 0.79% |
| 2024-09-26 | +10.0344% | +9.2924% | 0.74% |
| 2024-09-30 | +7.7864% | +7.2919% | 0.49% |

### 7.4 结论与对策

**东财 `stock_zh_a_hist(adjust="qfq")` 的收盘价序列在非除权日不满足复权恒等式，直接用它算收益率会产生系统性误差（本例中波动率虚高 1.2pp）。**

对策（三选一，需在 Step 1 定案）：

- **方案 A（推荐）**：收益率/波动率一律基于 **baostock 前复权序列** 或「**不复权价 × baostock 复权因子**」自行计算；东财只用于展示原始价格与成交量。
- **方案 B**：只用东财，但用其 `涨跌幅` 字段而非自算 `收盘.pct_change()`——需先验证该字段口径。
- **方案 C**：接入 tushare（`daily` + `adj_factor`），口径最规范。

> 无论选哪个，**必须在 `PriceRecord` 上显式存 `adjust_type` 与 `source` 字段**，并在报告里标注口径——否则「金融计算的正确性」（评分维度）无法自证。
### 7.5 新浪的 qfq 是可用的（东财/baostock 都挂时的备选）

2026-10-28 收盘前后实测：东财 `ConnectionError`、baostock 返回 0 行并报 socket 异常，
但**新浪的个股行情完全正常**（2.4s 取 3 年 923 行）。

用同一套决定性检验（非除权日「qfq 收益 == 不复权收益」）验证新浪：

| 指标 | 新浪 | baostock | 东财（对照） |
|---|---|---|---|
| 非除权日最大偏差 | **6.95e-06** | 0.00000000 | 7.87e-03 |
| 对年化波动率的影响 | **0.0026 pp** | 0 | **1.23 pp** |
| 判定 | ✅ 可用（舍入噪声） | ✅ 完美 | ❌ 口径有误 |

新浪的偏差量级是**小数点后第 6 位的舍入噪声**，比东财小 **467 倍**，对指标的影响可忽略。
在 `1e-5` 阈值下，915 个非除权日**全部通过**。

**代价**：新浪 `stock_zh_a_daily` **不带 PE / PB**，估值字段需要另取（或直接用申万映射表的快照）。

因此 Provider 的降级顺序定为：

```
baostock（口径完美，带 PE/PB） -> sina（口径正确，无 PE/PB） -> eastmoney（字段全，但 qfq 不能算收益率）
```

`PriceSeries.source` 会记录实际用的源，调用方据此决定能不能算波动率。

## 八、限频与重试（实测）

| 现象 | 实测 |
|---|---|
| 单次偶发失败 | 出现 `ConnectionError: RemoteDisconnected` |
| 退避后恢复 | 4s → 8s 退避后第 3 次成功，恢复约 10~15s |
| **持续拒绝** | 连续调用多个东财接口后，`stock_board_industry_hist_em`（行业板块历史）与 `index_zh_a_hist`（指数行情）**连续 3 次全部失败**，退避无效 |
| 行业板块清单 | 前 2 次失败，**第 3 次才成功**（496 个行业） |
| 非东财源 | `stock_financial_abstract`（同花顺）**完全不受影响**，0.7~0.8s |

**结论**：

1. 所有 Provider 必须内置 **指数退避重试（3 次，base 4s）+ 超时 + 降级到备源**——不加就现场演示失败。
2. **东财不能作为指数与行业数据的唯一来源**。一旦被限频，这两类数据会一起消失。§十 验证了完整可用的非东财替代方案。

## 九、推荐的组合方案

```
行情   ── 东财 stock_zh_a_hist（展示用）＋ baostock（指标计算用，复权口径正确）
公告   ── 巨潮 API（权威 PDF 全文，作 Evidence 引用源，PyMuPDF 抽取）
         ＋ 东财个股公告（全历史 + 87 种类型，作事件分类与检索）
         ＋ 东财全市场公告（每日一次，发现式扫描，异步 + 缓存）
新闻   ── 财联社电报 ＋ 东财快讯（流式落库，无历史回查）
         ＋ 东财个股新闻（补充）
财务   ── 新浪财务指标（86 列）＋ 财务摘要（同花顺）
估值   ── baostock 日频 peTTM/pbMRQ/psTTM/pcfNcfTTM（与行情同请求）
         ＋ 百度估值（辅助，近三年日频）
指数   ── 新浪 stock_zh_index_daily（主）＋ 中证官方（带指数 PE）＋ baostock
行业   ── 申万一级 index_hist_sw（最长历史）＋ 同花顺板块指数
辅助   ── 交易日历 / 停复牌 / 分红除权（baostock query_adjust_factor）
```

**tushare pro 可选升级**：接口最规范、`daily_basic` 直接给 PE/PB/换手率、`adj_factor` 复权因子权威，但需 token + 积分（公告 `anns` / 新闻 `news` 要较高积分）。

**baostock 是免费"正确性锚点"**：复权口径已验证正确，且有指数数据，但**没有公告和新闻**。

3. **粒度合适**：31 个行业里最小 20 只、最大 543 只股票，统计有意义；
   496 个会把样本打散，很多板块只有几只票。

## 附录 A、新闻采集的存储开销（实测）

探针：`scripts/probes/11_news_volume.py`
补充：用真实入库后的库文件复测（见 A.5），**修正了初版估算**。

### A.1 单条记录的真实体积

| 指标 | 实测值 |
|---|---|
| 正文字数（中位） | **141 字** |
| 有效内容（UTF-8） | 均值 484 B，中位 498 B，P95 769 B |
| 纯表 + 2 个普通索引 | **约 935 字节/行** |
| **加 trigram 全文索引后（实际使用）** | **2,845 字节/行** |

### A.5 重要修正：trigram FTS 占了 67%

初版探针用 `unicode61` 分词器测出「FTS 只多 17%」，但 `unicode61` 对中文不可用
（整句会变成一个 token），实际项目用的是 **`trigram`**，代价高得多。

用真实库（6,803 条）逐层剥离实测：

| 构成 | 大小 | 每行 |
|---|---|---|
| 完整（表 + 索引 + trigram FTS） | 18.46 MB | **2,845 B** |
| 去掉 FTS | 6.07 MB | 935 B |
| 再去掉一个普通索引 | 5.85 MB | 901 B |

> **trigram 索引单独占 1,910 B/行，是全部体积的 67%。**

这不是 bug，是中文子串检索的必要代价。如果真的嫌大，可以去掉 FTS 改用 `LIKE '%关键词%'`
——在 2 万行的量级下全表扫描也就几十毫秒，代价可接受。**体积能直接降到 1/3。**

### A.2 存储投影（按实测速率 227 条/天）

实际回溯 30 天得到 6,803 条，即 **227 条/天**（此前峰值外推的 600~1200 条偏高）。

| 采集时长 | 行数 | 含 FTS（实际） | 去掉 FTS |
|---|---|---|---|
| 1 个月 | 6,800 | **18.5 MB** | 6 MB |
| 3 个月 | 20,400 | **58 MB** | 19 MB |
| 6 个月 | 41,300 | 118 MB | 39 MB |
| 1 年 | 82,900 | 236 MB | 78 MB |
| 3 年 | 248,700 | 708 MB | 234 MB |

参考量级：一张手机照片 2~5 MB，一个 `node_modules` 通常 200 MB+。

### A.3 两个容易误解的点

1. **不是"占内存"，是占磁盘。** SQLite 是磁盘文件，查询只加载命中结果集。
   即使 10 万行，进程内存占用也在 MB 级。
2. **采集频率不决定存储量。** 5 分钟一采和 15 分钟一采，去重后的**新增条数是一样的**，
   频率只影响**请求次数**和**新闻延迟**，不影响库大小。存储量由新闻本身的产量决定。

### A.4 若确实要压体积（按性价比排序）

| 手段 | 效果 | 代价 |
|---|---|---|
| **去掉 trigram FTS，改用 LIKE** | **降 67%** | 检索改全表扫描，2 万行下仍够快 |
| 只采集自选股相关新闻（实体链接过滤） | 降 80%+ | 丢失全市场背景信息，B3 证据变少 |
| 正文截断到前 300 字 | 收益很小（本身中位才 141 字） | 几乎无 |
| 加保留期：90 天热数据 + 老数据归档/删除 | 恒定在 ~20 MB | 需写归档逻辑 |

**建议**：课程项目周期 3 个月，含 FTS 也就 **58 MB**，
**不要提前优化**，直接全量入库。等真的过 300 MB 再考虑砍 FTS。

## 附录 B、新闻历史能否回溯（实测 ✅ 可以）

探针：`scripts/probes/13_news_backfill_deep.py`、`14_backfill_horizon.py`

### B.1 东财新闻列表 —— 可回溯 48+ 天

接口：`GET https://np-listapi.eastmoney.com/comm/web/getNewsByColumns`
参数：`page_index` / `page_size=20` / `column=345`

| page_index | 最早时间 |
|---|---|
| 1 | 2026-10-28 02:53 |
| 10 | 2026-10-27 00:00 |
| 30 | 2026-10-22 15:13 |

| 120 | 2026-10-07 00:00 |

- 4780 条（page 1~240）跨越 **48.1 天**，平均 **99 条/天**
- **回溯 30 天只需翻到 page ≈150**（约 150 次请求）
- 未测到明显上限，48 天不是硬边界

### B.2 财联社电报 —— 可回溯，需自行算签名

接口：`GET https://www.cls.cn/v1/roll/get_roll_list`
关键参数：`last_time`（向前翻页）、`sign`

> `sign = md5(sha1(urlencode(params)).hexdigest())`
> akshare 的 `stock_info_global_cls` 只取第一页，没暴露 `last_time`，需自行实现。

实测连续翻 8 页拿到 160 条，回溯 5.1 小时（约 32 条/小时）。
翻 1 天约需 38 次请求，比东财贵。

### B.3 其他快讯源：只有快照

| 接口 | 条数 | 覆盖跨度 |
|---|---|---|
| `stock_info_global_ths`（同花顺） | 20 | 43 分钟 |
| `stock_info_global_sina`（新浪） | 20 | 14 分钟 |
| `stock_info_global_futu`（富途） | 50 | 2.3 小时 |
| `stock_info_global_em`（东财快讯） | 200 | 4.2 小时 |

这几个都**没有回溯能力**，只能作为「实时补充」的辅助源。

### B.4 这个结论改变了什么

因为**存在回溯通道**，采集器不需要 7×24 在线：

- 断线 1 天 → 下次回溯补齐
- 断线 1 周 → 东财 48 天的窗口内，仍可补齐
- 真正要保证的只是**至少每 2~4 周跑一次回溯**

这把「必须每天挂着采」降级成了「定期补一次」，容错性高得多。
